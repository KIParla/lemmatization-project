= Correzioni alla trascrizione originale: generare e applicare patch

Durante il lavoro di lemmatizzazione può capitare di individuare errori nella trascrizione originale (forme errate, notazione Jefferson scorretta, tokenizzazione sbagliata).
Questa guida descrive il workflow per riportare tali correzioni automaticamente nel file sorgente del corpus, senza interrompere il lavoro di lemmatizzazione.

== Concetto generale

Il file di lavoro (`.csv` nella cartella `wip/`) è l'unico punto in cui si modificano i dati.
Le correzioni alla trascrizione non vengono applicate direttamente al repository del corpus: viene invece generato un file `.patch` (diff unificato) che può essere applicato sul branch `dev` del modulo corrispondente con un semplice `git apply`.

In questo modo:

* il lavoro di lemmatizzazione procede in modo autonomo;
* le correzioni alla trascrizione vengono proposte in modo tracciabile e revisionabile;
* è sempre possibile aggiornare la patch se il file sorgente viene nel frattempo modificato.

== Struttura delle cartelle

[source]
----
lemmatization-project/
├── wip/
│   └── KIP/
│       └── BOA1007.csv          ← file di lavoro con lemma/upos + correzioni
├── patches/
│   └── KIP/
│       ├── BOA1007.vert.tsv.patch       ← patch da applicare al corpus
│       ├── BOA1007.vert.tsv.pos.patch   ← (se serve) patch di lemma/upos, da applicare dopo
│       └── BOA1007.vert.tsv.recap.md    ← riepilogo delle modifiche
└── make_patch.py                ← script per generare la patch
----

== Cosa si può correggere nel CSV

Nel file di lavoro `.csv` le seguenti colonne vengono propagate nella patch:

[cols="1,3"]
|===
|Colonna |Descrizione

|`span`
|La forma trascritta in notazione Jefferson (es. `[s:ì].` al posto di `[ssì].`)

|`form`
|La forma ortografica normalizzata (es. `sostituire` al posto di `sostiuire`)

|===

Le colonne `lemma` e `upos` non fanno parte della trascrizione, ma `make_patch.py` le aggiunge comunque alla patch (con la stessa logica di `wip2tsv.py`): vedi <<lemma-upos>>.

=== Modifiche strutturali: unire token

Se durante la lemmatizzazione si stabilisce che due token vanno uniti (es. `elle` + `due.` → `elledue.`), è sufficiente:

. Nel CSV, eliminare la riga del secondo token e aggiornare `span` e `form` del primo.
. Lo script rileva automaticamente l'assenza del secondo token nel CSV e lo elimina dalla patch.
. Il timestamp `End=` del token eliminato viene trasferito automaticamente al token risultante.

[TIP]
====
In caso di eliminazione, lo script produce un file `.recap.md` con tutte le informazioni del token rimosso.
Controlla sempre il recap per verificare se ci sono colonne come `overlaps` o `prolongations` che richiedono un aggiustamento manuale.
====

== Generare la patch

Lo script `make_patch.py` si trova nella cartella `tools/` del progetto KIParla.

Dalla cartella `lemmatization-project/`, eseguire:

[source,bash]
----
python3 ../tools/make_patch.py wip/KIP/BOA1007.csv ../moduli/KIP/tsv/BOA1007.vert.tsv
----

Lo script produce:

* `patches/KIP/BOA1007.vert.tsv.patch` — il file di patch
* `patches/KIP/BOA1007.vert.tsv.pos.patch` — la patch di lemma e upos, solo se il TSV non ha ancora le PoS (vedi <<lemma-upos>>)
* `patches/KIP/BOA1007.vert.tsv.recap.md` — riepilogo delle modifiche strutturali e di lemma/upos (se presenti)

L'output indica quante righe vengono aggiunte/modificate/rimosse:

[source]
----
Patch written: patches/KIP/BOA1007.vert.tsv.patch  (+6 / -9 lines)
Recap written: patches/KIP/BOA1007.vert.tsv.recap.md  (3 items)
----

Per un file di un corpus diverso (es. `KIPasti`), il percorso del TSV cambia di conseguenza:

[source,bash]
----
python3 ../tools/make_patch.py wip/KIPasti/TOA1001.csv ../moduli/KIPasti/tsv/TOA1001.vert.tsv
----

[[lemma-upos]]
== Lemma e upos nella patch

Oltre alla trascrizione, la patch porta `lemma`, `upos` e le righe sintattiche dei token composti (`5-7a`, `5-7b`, con `type` `syntactic`). Lo script le calcola applicando `wip2tsv.py` al TSV già corretto dalla trascrizione, e confronta il risultato con il sorgente. Quanti file escono dipende dal TSV sorgente:

[cols="2,3"]
|===
|Il TSV sorgente...|Cosa produce lo script

|non ha ancora lemma/upos
|*Due patch*, da applicare in quest'ordine: `CODICE.vert.tsv.patch` (solo trascrizione) e poi `CODICE.vert.tsv.pos.patch` (lemma, upos e righe sintattiche).

|ha già lemma/upos
|*Una sola patch*, con trascrizione e annotazione insieme. Se non c'è nulla da cambiare, non scrive niente.

|non concorda con il CSV sui token (es. token da aggiungere a mano, vedi il recap)
|Solo la patch di trascrizione, e un avviso `Lemma/upos NOT added`. Applicata la patch e aggiunti i token a mano, rilanciare lo script.
|===

La patch delle PoS è calcolata sul TSV *dopo* la patch di trascrizione: va applicata sempre per seconda.
Se il TSV cambia in mezzo, `git apply --check` fallisce per il contesto e bisogna rigenerare entrambe.

Le conversazioni già integrate (con PoS) non hanno più una patch quando `wip/` e TSV coincidono; se invece il CSV è stato corretto dopo l'integrazione (es. parole incomprensibili normalizzate a `x`/`X`), lo script scrive una nuova patch unica, con l'aggiornamento da applicare su `dev`.

== Leggere il recap

Prima di applicare la patch, leggere il file `.recap.md`.
Ogni voce indica cosa è successo ai token eliminati o aggiunti:

[cols="1,3"]
|===
|Marcatore |Significato

|✅ auto-transferred
|Il timestamp `Begin=` o `End=` del token rimosso è stato trasferito automaticamente al token adiacente.

|⚠️ manual check needed
|Una colonna come `overlaps` o `prolongations` del token rimosso conteneva un valore non vuoto.
Va verificato manualmente nel file sorgente dopo aver applicato la patch.

|❌ conflict
|Si è verificato un conflitto nel trasferimento dei timestamp.
Richiede intervento manuale prima di applicare la patch.

|**ADD**
|Un token presente nel CSV non esiste nel TSV.
L'inserimento non può essere automatizzato: va fatto a mano nel sorgente.
|===

In fondo al recap c'è la sezione *Lemma e upos*: dice se le PoS sono nella patch unica o nella `.pos.patch` (da applicare dopo), quanti token vengono annotati per la prima volta, quanti hanno lemma o upos modificati (con l'elenco, se pochi) e quante righe sintattiche si aggiungono o tolgono.
Se non ci sono modifiche strutturali ma ci sono differenze di PoS, il recap contiene solo questa sezione.

== Verificare la patch

Prima di applicarla, verificare che la patch sia valida:

[source,bash]
----
cd /path/to/KIP
git checkout dev
git apply --check ../lemmatization-project/patches/KIP/BOA1007.vert.tsv.patch
# se esiste anche la patch delle PoS, dopo aver applicato la prima:
git apply --check ../lemmatization-project/patches/KIP/BOA1007.vert.tsv.pos.patch
----

Se non viene restituito nessun errore, la patch è applicabile.

[NOTE]
====
Se il file sorgente è stato modificato dopo la generazione della patch (es. un'altra patch è già stata applicata), il controllo potrebbe fallire con un errore di contesto.
In questo caso, rigenerare la patch dallo stesso CSV aggiornato:

[source,bash]
----
python3 ../tools/make_patch.py wip/KIP/BOA1007.csv ../moduli/KIP/tsv/BOA1007.vert.tsv
----
====

== Applicare la patch

[source,bash]
----
cd /path/to/KIP
git checkout dev
git apply ../lemmatization-project/patches/KIP/BOA1007.vert.tsv.patch
git apply ../lemmatization-project/patches/KIP/BOA1007.vert.tsv.pos.patch   # solo se esiste
----

Dopo l'applicazione, fare il commit sul branch `dev` (un commit per la trascrizione e uno per le PoS, se le patch sono due):

[source,bash]
----
git add tsv/BOA1007.vert.tsv
git commit -m "fix(tsv): lemmatization-project review of BOA1007 (transcription, spans and features)"
# dopo la seconda patch:
git commit -am "feat(tsv): lemma, upos and syntactic rows for BOA1007"
----

Se il recap segnalava voci con ⚠️, applicare prima la patch, poi correggere manualmente le colonne interessate, e includere tutto nello stesso commit.
