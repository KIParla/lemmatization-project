= Pipeline: dal CSV lemmatizzato al modulo KIP

Questa guida descrive, passo per passo, come portare una conversazione lemmatizzata (`wip/<modulo>/<codice>.csv`) nel repository del modulo, sul branch `dev`: correzioni alla trascrizione, lemma e UPOS, file `.eaf` e lineari.
Gli esempi usano KIP e `BOA1002`; i comandi si lanciano dalla cartella `lemmatization-project/`, con i repository affiancati (`../tools`, `../moduli/KIP`).
Il dettaglio delle patch è in xref:patching.adoc[].

[IMPORTANT]
====
L'ordine dei passi conta.
La patch si genera e si applica *prima* di aggiungere lemma e UPOS, e il TSV non va ripatchato dopo averla applicata: eventuali ritocchi successivi si fanno direttamente nel TSV.
====

== 1. Generare la patch e il file di review

[source,bash]
----
python3 ../tools/make_patch.py wip/KIP/BOA1002.csv ../moduli/KIP/tsv/BOA1002.vert.tsv
----

Il percorso del TSV va passato esplicitamente: quello dedotto dallo script (`../KIP/tsv/`) non coincide con `../moduli/KIP/tsv/`.

Lo script scrive in `patches/KIP/`:

* `BOA1002.vert.tsv.patch`: la patch da applicare;
* `BOA1002.vert.tsv.recap.md`: elenco delle modifiche (mod/del/agg) e delle voci da verificare;
* `BOA1002.review.csv`: copia del CSV con due colonne in più, `merge` (`OK`, `WARN`, `FAIL`) e `note`, su cui si fa la revisione;
* `.review-base/BOA1002.csv`: istantanea del CSV al momento della generazione, serve a riportare le tue modifiche nel `wip/` (non toccarla).

== 2. Rivedere

Apri `BOA1002.review.csv` e controlla le righe con `WARN` o `FAIL` e le voci `[ ]` del recap.
Tipicamente: forma non derivabile dallo span (`WARN`), token duplicati, `overlaps`/`prolongations` da sistemare.

Il review è l'unico posto in cui si lavora: si possono correggere celle (`span`, `form`, `lemma`, `upos`, ...) e anche aggiungere, togliere o spostare righe, unire token (`elle` + `due` → `elledue`) e creare righe `a`/`b` per i token multiparola.
Alla rigenerazione `make_patch.py` riporta tutto nel `wip/` (stampa `Riportate in <codice>.csv le modifiche …`) e rigenera patch, recap e review.

[WARNING]
====
Non modificare lo stesso file contemporaneamente in `wip/` e nel review.
Se il `wip/` è cambiato dopo la generazione del review *e* nel review hai cambiato le righe, le due versioni non si possono unire: lo script stampa `ERRORE … NON riportate` e non tocca né il review né il `wip/` (nessun lavoro va perso).
In questo caso porta a mano le modifiche in un solo dei due file e rigenera il review.
Se hai cambiato solo celle, le due versioni si uniscono cella per cella (se la stessa cella è cambiata in entrambi vince il `wip/` e viene segnalato un `CONFLITTO`).
====

Le righe con `FAIL` o `WARN` e le voci `[ ]` del recap indicano cosa guardare:

* `WARN`: forma non derivabile dallo span; `overlaps`/`prolongations` di un token eliminato da riassegnare a mano nel TSV dopo l'applicazione;
* `FAIL`: token_id duplicato nel CSV (da correggere); oppure conflitto di timestamp su un token eliminato (avviso, non blocca la patch: i timestamp del token eliminato si perdono).

Dopo ogni correzione rilancia il comando del passo 1 finché il recap indica *0 da verificare*.
Se il recap segnala cose strane nei dati (es. un token duplicato dopo un'aggiunta, `rispetto a quel quel programma`), correggi il `wip/` e rigenera.

== 3. Applicare la patch su `dev`

[source,bash]
----
cd ../moduli/KIP
git checkout dev && git pull
git apply --check ../../lemmatization-project/patches/KIP/BOA1002.vert.tsv.patch
git apply ../../lemmatization-project/patches/KIP/BOA1002.vert.tsv.patch
git add tsv/BOA1002.vert.tsv
git commit -m "fix: transcription corrections from lemmatization of BOA1002"
----

Se `--check` fallisce per il contesto, il TSV è cambiato dopo la generazione: rigenera la patch (passo 1).
Un commit per conversazione.

Se nel recap c'erano voci `ADD` o `⚠️`, sistemale a mano nel TSV prima del commit.
Ritocchi che emergono dopo (es. fondere due intervalli `overlaps`) si fanno nel TSV e si committano a parte; la patch in `patches/` non va riapplicata.

== 4. Aggiungere lemma e UPOS

[source,bash]
----
python3 ../tools/wip2tsv.py wip/KIP/BOA1002.csv ../moduli/KIP/tsv/BOA1002.vert.tsv -o /tmp/BOA1002.vert.tsv
diff /tmp/BOA1002.vert.tsv ../moduli/KIP/tsv/BOA1002.vert.tsv | head   # controllo
python3 ../tools/wip2tsv.py wip/KIP/BOA1002.csv ../moduli/KIP/tsv/BOA1002.vert.tsv
----

(senza `-o` il TSV viene riscritto sul posto; l'operazione è idempotente.)

Lo script scrive `lemma` e `upos`, e per i token multiparola (`sulla` = `su` + `la`) lemma e UPOS delle parole uniti da `+` (`su+la`, `ADP+PRON`) più una riga `type=syntactic` per parola.
Rifiuta di scrivere se TSV e CSV non concordano su token o forme: vuol dire che la patch del passo 3 non è stata applicata (o che il CSV è cambiato), `--force` solo se sai perché.

[source,bash]
----
git add tsv/BOA1002.vert.tsv
git commit -m "feat(tsv): lemma, upos and syntactic rows for BOA1002"
----

== 5. Rigenerare `.eaf` e file lineari

Dalla cartella `tools/`, con il suo ambiente virtuale:

[source,bash]
----
cd ../tools
.venv/bin/python sync.py --from-vert ../moduli/KIP/tsv/BOA1002.vert.tsv --audio-ext mp3
----

Questo riscrive `eaf/BOA1002.eaf`, `linear-enriched/BOA1002.txt` e `linear-orthographic/BOA1002.txt` (le righe `syntactic` sono ignorate).
Gli avvisi `participant ??` sul rapporto di validazione sono già presenti e non dipendono da questo lavoro.

Controlla `git diff --stat` in `moduli/KIP`: le differenze devono corrispondere alle correzioni della patch (poche righe per conversazione).
Se compaiono molte righe diverse, qualcosa non va (es. spazi inattesi dopo gli apostrofi).

[source,bash]
----
cd ../moduli/KIP
git add eaf linear-enriched linear-orthographic
git commit -m "chore: regenerate eaf and linear files of BOA1002"
git push origin dev
----

== 6. Chiudere nel lemmatization-project

* Committare `patches/<modulo>/` (patch, recap, `.review.csv` e `.review-base/`) e i `wip/` corrispondenti.
* Aggiornare `TODO.md` (conteggi e liste: è un'istantanea, non si aggiorna da solo).
